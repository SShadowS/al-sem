## Design

Rounds 1 and 2 of the spec panel (sol S1-S13, SN1-SN3; opus O1-O13, ON1-ON3) reshaped this section; each fix names its finding ids. After round 2 the conductor narrowed the scope: global-config reload and `.git`-boundary moves are out (see Non-goals).

### Goal and non-goals

Goal: (1) delete the unused `salsa` dependency, byte-neutral; (2) make the LSP's per-root watcher see every input the LSP build and the server read, from the moment before the first read, so no file edit, rename, move, replacement, dependency-cache change or config change leaves a stale snapshot or stale diagnostics until restart; and stop rebuilding the world for files nothing reads.

Non-goals, each a stated limit:
- **Live reload of the GLOBAL config** (`~/.al-sem/config.json`, legacy `~/.al-call-hierarchy/config.json`): an edit still needs a server restart, as today. Reason: rare, and the home-folder and state-folder watches it needs are what made the round-1 design race-prone (S6, S7, SN1-SN3, ON1).
- **A move of the `.git` boundary** (a `.git` created or removed at the root or an ancestor): the ancestor walk is fixed when the watcher starts, so such a move still needs a restart. Reason: rare, and watching the boundary made every Windows `git` operation a candidate full rebuild (ON1).
- 13b (incremental L4 host, invalidation rule, off-thread worker, `--l4-host`); Q4 (retry after a failed first BUILD: a root whose build fails still ends up with no watcher; races after a successful build are in scope, S7); `--no-watcher` sessions (they see only `.al` `didSave`s, as today); a watcher stop channel (a leak, not blindness); Windows/macOS event measurement (no machine here: the design does not depend on rename pairing or on file/folder typing, see F5).

**One enumerator, one predicate (I11; S11, O13).** `dependencies.rs` gains `package_cache_scope(root) -> CacheScope { candidates, walked_dirs }`, the ONLY implementation of the folder walk: the own `<root>/.alpackages` plus, unless `<root>/.git` exists, each ancestor's `.alpackages`, stopping after an ancestor holding `.git` or at 8 levels (today's rules, `dependencies.rs:357-392`), WITHOUT the `is_dir` test. `walked_dirs` lists every ancestor the walk visited. `find_all_alpackages_folders` becomes `candidates` filtered by `is_dir` + the existing `paths_equal` dedup: byte-neutral, pinned by the existing tests `dependencies.rs:1606-1769` and the closure digest. `discover_app_files`'s `.app` test becomes a named `is_app_file(name)` (case-sensitive, exactly as `:425`) used by both the loader and the predicate. `cache_scope_role(&CacheScope, path) -> Option<Role>`: `CacheFolder` when `path` is a candidate; `AppFile` when `path`'s parent is a candidate and `is_app_file(path.file_name())` on the RAW name (O13). Folder parts compare after `protocol::normalize_path` on both sides (the house case rule). The watcher computes the scope ONCE when it starts (the boundary is frozen, Non-goals); later only WHICH candidates exist is re-checked. `server.rs`'s `path_is_dependency_source` and `watcher.rs`'s `.alpackages` name test are deleted; nothing else tests the folder name.

**Root containment (S3).** One helper `rel_under_root(root, p) -> Option<rel>` decides containment by comparing the `protocol::normalize_path` forms of `root` and `p` component by component, and takes `rel` from `p`'s OWN components (disk case) after the root's component count. Mapping rules 5-6 and `reconcile` rule 1 call it before anything else, so a Windows path whose root part differs in case from the lowercased root is still under the root, and the vp keeps the disk's case.

**Watch plan and watch state (task 3; S4, S8, O1, SN2).** `watcher.rs` holds:
- `trait WatchBackend: Send { fn watch(&mut self, &Path, RecursiveMode) -> notify::Result<()>; fn unwatch(&mut self, &Path) -> notify::Result<()>; }`, implemented for `RecommendedWatcher` and by a recording fake in tests. Raw events reach the loop on a `Receiver<notify::Result<Event>>`.
- `WatchScope { root, cache: CacheScope }`, computed once at start, and `watch_plan(&WatchScope) -> BTreeMap<PathBuf, RecursiveMode>`: the root recursive; each `walked_dirs` entry non-recursive (to see a candidate cache folder appear, vanish or be replaced); each candidate cache folder outside the root that exists now, non-recursive. No home or state-folder watch. If one path is planned twice, `Recursive` wins (SN2; only reachable when the root itself is a candidate folder).
- `WatchState { scope, registered, cache_seen, failed }` with `start(backend)` and `handle_raw(&mut self, backend, raw, &ConfigHandle, &Sender<ChangeEvent>)`, the ONE per-event step the production loop runs. `cache_seen` records, per candidate outside the root, whether it existed as a folder at the last check. `resync(backend) -> bool` re-stats every candidate, watches each that now exists and is not registered, unwatches each that no longer exists, updates `cache_seen`, and returns whether any existence changed.
- `start` registers the root and the `walked_dirs` FIRST, then stats the candidates and registers the existing ones (S7: a cache folder created between the two steps is seen by its parent's watch).
- Order rule (S4): `resync` always runs BEFORE the `DepsChanged` it causes is sent, so the rebuild's disk read happens after the new watch exists. A `DepsChanged` from any source also triggers `resync` first ("re-synced after a rung 3").
- Failed registrations (S4, F10): kept in `failed`, retried by the loop every 5 s (it already wakes every 100 ms). A retry that succeeds runs `resync` and THEN sends `DepsChanged` (a cache path or walked dir) or `Overflow` (the root), so a cache folder created while its parent's watch was failing is registered before the rebuild reads (round-2 S4).

**Event kinds (ON1), used ONLY by mapping rules 4 and 6.** **Structural**: `Create(_)`, `Remove(_)`, `Modify(Name(_))`; they say an entry appeared, vanished or moved. **Touched**: `Modify(Any)`, `Modify(Other)`, `Modify(Data(_))`, `Modify(Metadata(_))`, `EventKind::Any`, `EventKind::Other`. On Windows a folder gets `Modify(Any)` whenever a child is created, deleted or renamed (its last-write time moves), so a Touched event on a folder never says the folder itself appeared, vanished or changed type. The split decides only whether the root's own entry or a cache folder sends `Overflow`/`DepsChanged`. Source reconciliation in the updater does NOT depend on the event kind (round-3 rule, below).

**Event mapping (task 3)**, `map_event(&WatchScope, &notify::Event) -> Vec<ChangeEvent>`; pure, and called only from `handle_raw`. `FileChange` and `server.rs::to_change_event` are deleted. First match wins, per path:
1. `need_rescan()` → `Overflow` (today's rule).
2. `EventKind::Access(_)` → drop. It must precede rule 4: the loader's own reads produce `Access(Open)` on cache paths (P10), so without it every rung 3 would trigger another (O8).
3. `<root>/.al-sem.json` or `<root>/.al-call-hierarchy.json` → `ConfigChanged` (any kind but Access).
4. `cache_scope_role` = `CacheFolder`:
   - OUTSIDE the root (the only candidates in the plan and in `cache_seen`): a resync request; `handle_raw` sends `DepsChanged` only if `resync` reports an existence change, or the kind is Structural (a replaced folder keeps its name, so the existence diff alone can miss it; a Structural kind forces `unwatch` + `watch` of that folder, then `DepsChanged`). A Touched event on an unchanged cache folder sends nothing (ON1).
   - INSIDE the root (`<root>/.alpackages`, covered by the recursive root watch, which notify re-arms for re-created subfolders itself): a Structural kind → `DepsChanged`, with no `unwatch`/`watch` (O3N2: the root watch owns that folder's sub-watch); a Touched kind → nothing.
   - `AppFile` → `DepsChanged` (any kind but Access).
5. not under the root (`rel_under_root` is `None`) → drop.
6. the root's own entry (seen through an ancestor watch): a Structural kind → `Overflow`; a Touched kind → nothing (ON1: every child write in the root moves the root's last-write time on Windows).
7. `<root>/app.json` → `DepsChanged`.
8. any path under the root with a `.git` component (`<root>/.git`, and a submodule's or nested repository's `.git` deeper down) → drop (O3N1). Git rewrites `index.lock` on every `git status`, which VS Code runs on each save; reconciling `.git` on each would walk `objects/`. Stated divergence: the build's walk does not skip `.git` (`source_text.rs:26`), so a `.al` file placed inside a `.git` folder would be built but not watched.
9. any other path under the root → `PathChanged(path)` whatever the extension (S1, S10); except a `Modify(Data|Metadata)` on a path without `.al` extension → drop. A `Name(Both)` yields one `PathChanged` per path. The watcher never emits `FileSaved` or `FileRemoved` (O3).

**Updater: one disk reconciliation (task 2; S1, S2, S3, S12, O3, O4, O5, ON2, ON3, S3N1-S3N5, O3N1).** New `ChangeEvent::PathChanged(PathBuf)`, with no kind attached. In `classify`, `PathChanged`, `FileSaved` and `FileRemoved` all go through `reconcile(path)`. The result depends only on the disk and on the recorded stamps, never on the event kind or on how events were coalesced (S3N1): any number of events for a path, in any order, reconcile to the same plan. For each event path `p`:
1. `rel_under_root(root, p)` is `None` → rung 3 (fail closed, as today). `p` is the root → `Overflow` (O5).
2. A component of `rel(p)` is a `SKIP_DIRS` name → nothing (`Ignored`; W7). The test `file_saved_under_dependency_dir_escalates_to_rung3` is renamed and asserts no new generation: its premise (a `.al` under `.alpackages` is dependency source) is false (P8).
3. `affected` = known vps equal to `rel(p)` or starting with `rel(p) + "/"`, exact. If none match exactly but a known key `K` matches ignoring ASCII case (S3, O4, ON3):
   - `fs::canonicalize` fails for `p` or for `root.join(K)` while `p` exists (identity unknown: permissions, a dangling link) → `Overflow` (S3N4). A failed rung-3 rebuild keeps the old snapshot (`apply_rung3` returns `None`, `updater.rs:642-662`), so nothing is lost or duplicated.
   - `p` exists and both canonicalize to the same file (a case-insensitive file system): `PathChanged` → `Overflow` (a case-only rename; the new spelling must come from a fresh walk); `FileSaved` → reconcile `root.join(K)` instead of `p` (the H-10 fallback, `updater.rs:1034-1062`).
   - `p` exists and both canonicalize to DIFFERENT files (a case-sensitive file system holding both `target.al` and `Target.al`) → `p` is its own vp; the fallback does not apply (ON3).
   - `p` does not exist: `FileSaved` → reconcile `root.join(K)` (H-10); `PathChanged` → nothing.
4. Stat `p` with `fs::metadata` (follows links, like the walk):
   - a regular file: when `has_al_extension`, it is the event's own file → always read (stat recorded first, see Stamps) → a save of its vp; a read error `NotFound` → absent; any other read error → keep that vp's last-known state (fail closed, today's skip).
   - a folder, whatever the event kind (the ONE folder rule): `source_text::discover_al_files(p, NestedApps::Walk)`, the build's own walk with its skip folders, over the WHOLE subtree → the found set; a walk error → `Overflow`.
   - `Err` with kind `NotFound` or `NotADirectory` → absent (S2: a path whose parent became a file).
   - any other `Err` → `Overflow`.
5. Removal: every `affected` vp (equal to `rel(p)` or anywhere under `rel(p)/`, nested subtrees included, S3N2) that the stat or the walk did not find → `Planned::Remove`. This covers a known file replaced by a folder, a folder replaced by a file, and a subfolder moved out. An absent `p` with no `affected` vp → nothing (no rung 2 for a temp file).
6. Reads for files the folder walk found (S12, ON2, S3N5): a file whose vp is unknown → read and parsed. A file whose vp is known → `fs::metadata` only; read ONLY when its stamp differs from the recorded one (or none is recorded), and then plan nothing if the text equals `cur.parsed[vp].text` (the stamp is still updated). So a folder event re-reads no unchanged file, and a folder replaced by one with the same file names is re-read wherever a stamp moved. The event's own file (rule 4, first bullet) is always read: unchanged editor saves keep today's rung-1 apply, which tests rely on (probe "No-op save semantics").
7. Plans are keyed by vp and deduplicated. Within one `classify` call a vp can be observed twice (by a folder walk and by its own stat), and a delete-then-recreate can fall between the two; the LATER observation wins, deterministically. The end state stays correct either way, because a disk change after an observation raises a new event that reconciles again.

**Stamps (task 2; S3N5, ON2, S4N1).** `Updater` gains `stamps: HashMap<String, FileStamp>` keyed by vp, where `FileStamp` is `(len, modified)` plus `(dev, ino)` on Unix (`std::os::unix::fs::MetadataExt`; Windows has no stable file id in `std`). Lifecycle (S4N1): **a stamp only ever certifies text the updater itself read right after taking it.** The map starts EMPTY after every full build (the initial one in `spawn_updater`, and every rung 3); there is no post-build seeding, because metadata taken after the build's read cannot prove the indexed text is current (a folder replaced between the two would get its NEW stamp certified, and folder moves raise no per-file events, P10). A stamp is set only from a stat taken BEFORE a read the updater makes, paired with that read's text (indexed, or found equal to `cur.parsed[vp].text`), so a write racing the read leaves an older stamp that differs next time and forces a re-read; it is removed with each `Planned::Remove`. Consequence: the first folder event after a full build reads each known file under that folder once (no parse and no generation when the text is equal); later events on it read only files whose stamp moved. The build's input reader (`src/program/inputs.rs`) is not changed: carrying a stamp from the build's own read would need a field through `WsFile` → `SourceFile` → `ParsedFile`, a wider change for a one-time saving. Cost: no work per full build; memory: one vp `String` plus about 32 bytes per stamped file, under 1 MB at CDO's file count; per folder event, one subtree walk plus one stat per file under the folder, plus the one-time reads above. Limit: a file replaced, without its own event, by one with the same length and mtime (and, on Windows, any id) after it was stamped is not re-read (F16).

**Staged stamps (task 2; A2O1).** Stamps taken while a batch is classified are STAGED with that batch's plan, not written to `stamps` at once. They are committed only when the plan is applied: a rung-1 or rung-2 apply, or a no-op batch (its reads found text equal to `cur.parsed`, which is already published). A batch that escalates to rung 3 discards its staged stamps. A successful rebuild empties the map anyway; a rebuild that returns `None` keeps the old snapshot AND the old map, so no stamp ever vouches for text that was read but never indexed. Test: T15(b) — a batch forced to rung 3 (it also holds `DepsChanged`) whose rebuild fails (`app.json` made invalid), after its reads of a changed `src/a.al`; then a folder event on `src` → `a.al` is re-read and indexed, equal to a fresh build once `app.json` is restored. Break: commit stamps during classify → the read is skipped and the old text stays.

**`ConfigChanged` → full republish (task 2; O12).** The inner loop of `spawn_updater` scans each gathered batch for `ConfigChanged` and carries that flag out of the inner loop together with the decision (`break (decision, config_changed)`). With the flag set: a no-op batch calls `on_swap(&cur, &SwapScope::Full)` with no new generation; a rung-1 batch publishes `SwapScope::Full` instead of its delta; rung 2 and rung 3 already publish `Full`; a rung 3 whose rebuild returns `None` (`updater.rs:1226`) calls `on_swap(&cur, &SwapScope::Full)`, so the config change is never lost to a failed build.

**Config sharing and reload (task 3; S9, O2, O6, O7, SN1).** One `ConfigHandle` per root, shared by `ServerState`, the `on_swap` closure and the watch loop: an `RwLock` over `(DiagnosticConfig, reloaded: bool)`. Readers clone the config under the lock and release it before any work; no guard is held across `compute_all` or code lens (O6). In `handle_raw`, a `ConfigChanged` first reloads (`DiagnosticConfig::load(root)`, then `disable_all()` under `--no-diagnostics`), stores it with `reloaded = true`, then sends the event. The startup install is `install_initial(cfg)`, which stores only while `reloaded` is false (SN1): a reload that ran during startup read the file later, so it always wins, whichever of the two writes lands first. Startup does not need to be serialized with the loop. `on_swap` with every detector off no longer returns early when this root has published diagnostics: it publishes the diff against an empty map (each URI gets one empty notification), without calling `compute_all`; when nothing was published it still sends nothing (`all_detectors_disabled_publishes_no_diagnostics` keeps passing).

**Startup order (task 3; S7).** `RootState::state` creates the channel and the config handle, starts the watch state (`start` registers the root and `walked_dirs` first, then the existing candidate folders, on the calling thread), and only then installs the initial config and builds the snapshot; the updater then drains the events that arrived during the build. Any change after registration is evented; any change before it is in the read. `build_server_state` takes the channel and the handle instead of creating them (a stated test change for its callers). When the build fails, the receiver is dropped and the watch thread exits at its next send (stated, Q4 territory). `RootBuild` gains the backend factory (production: `RecommendedWatcher`), so tests inject a fake.

### False-positive and failure shapes

- **S1 churn**: temp files under the root produce events; they become `PathChanged` of a non-folder with no known vp → nothing. `.git` is dropped outright (rule 8). Touched events on the root's own entry and on unchanged cache folders send nothing (ON1). Cost: a wake-up and a key scan per debounced batch. Accepted, stated.
- **S2 folder events**: any event on a folder costs one walk of its subtree plus one stat per file under it, and reads only new files or files whose stamp moved. On Windows that happens on every child create/delete/rename in a folder (its own `Modify(Any)`), so the walk is of that folder's subtree, not the workspace. A big folder rename: one read per moved file (they are new vps), rung 2, equal to or cheaper than rung 3.
- **S3 backend differences** (Windows/macOS not measured): no rule depends on rename pairing, on the event kind (for source) or on coalescing; only `Modify(Data|Metadata)` on non-`.al` paths is dropped. See F5.
- **S4 case**: Windows roots are lowercased (`protocol.rs:34`); containment and cache/config folder parts compare normalized (`rel_under_root`); vps compare exactly; a case-only rename on a case-insensitive file system takes rung 3; case twins on a case-sensitive one stay two vps.
- **S5 dependency cache appears, vanishes or is replaced**: `resync` re-registers before the rebuild reads; no gap. A `.git` boundary move and global-config edits are NOT seen (Non-goals; Discoveries).
- **S7 startup**: parent watches exist before the candidates are stat-ed, and all watches exist before the first read; a config reload during startup always beats the initial install (SN1).
- **S8 disabling all detectors** clears published diagnostics, without `compute_all`.
- **S9 a failed first build**: the watch thread lingers until its next send fails. Q4 territory, stated.
- **S10 registration refused** (permissions, inotify limit): retried every 5 s; the shape is covered once a retry succeeds.
