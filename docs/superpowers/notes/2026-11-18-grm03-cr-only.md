# GRM-03: CR-only line ends break directive parsing

## What happens

In a source file with CR-only line ends (classic Mac), a `#if` or a `//` comment never ends, so
the file's objects vanish from the model.
- **With a `#if`:** the file parses to one ERROR node.
- **With a `//` comment** (found in the Fable review): a header comment makes the whole file one
  comment, a CLEAN parse with no object; a comment inside a body eats the rest and gives an ERROR.
- **Version:** tree-sitter-al v5.3.0 (`9d155ee7`), re-checked 2026-11-18.
- **Clean cases:** the same text with LF or CRLF line ends parses clean.

## Cause: the grammar, not al-sem

- The grammar's external scanner (`src/scanner.c`) ends every directive line at `\n` only. Its
  loops and end checks test `lexer->lookahead` against `\n` alone, so a lone `\r` never ends the
  line.
- The line comment token is `token(seq('//', /[^\n]*/))` in `grammar.js`, so it also runs past a
  lone `\r`.

al-sem's own line-end handling plays no part.

## Done here

- **al-sem reports the loss.** A workspace file with no object is a `DIAG-parse` warning when its
  parse failed or when it has a lone-CR line end (even with a clean parse). A lone-CR file gets
  the likely cause named (CHANGELOG, GRM-03).
- **The grammar fix is filed upstream:** https://github.com/SShadowS/tree-sitter-al/issues/45.
  The issue holds a synthetic repro only, the scanner lines, and the suggested `is_line_end` change.
  A follow-up comment adds the `//` comment token, with a synthetic repro and a one-line fix.
- **Owner's decision:** file and report it; no known-limit entry.

## How common

0 of 12,277 real files:
- CDO baseline (`bc3ccb18`): 582 workspace files and 10,881 dependency files. All have LF; two
  dependency files have no line end at all.
- DO checkout (`b3b4459`): 814 files, all with LF.

## What the compiler does

alc 18.0.41.62505 (`/opt/al-tool`, .NET 10, Linux) accepts such files and keeps their objects. It
compiled four one-file projects, and each app's `SymbolReference.json` held the codeunit with
method `P`:
- the `#if` repro with LF (control);
- the same text with CR-only line ends;
- a CR-only file starting with a `//` header comment;
- a CR-only file with a `//` comment inside a body.

So the compiler ends `#if` lines and `//` comments at a lone CR, and the grammar is wrong. The
result is on issue 45.
